Chapter 1

Requirements

1.1Introduction

1.1.1Project overview

Tujitunze (HSIMS — Health Savings and Insurance Management System) is a community-based health savings platform for Tanzania. It lets a member accumulate a personal health fund from the mobile money, airtime, and bank activity they already do every day, and routes a share of each contribution into that member's insurance cover automatically.

The platform is a Next.js (App Router) frontend over a NestJS + TypeORM + PostgreSQL backend, organised around seven operating roles — Member, Admin, Bank, Telecom, Insurance, Super-admin, and the currently-inactive Hospital role — each with its own guarded API surface and, for six of the seven, its own operational dashboard.

1.1.2Problem statement

  • Low formal health-cover penetration. Many Tanzanians who transact daily through mobile money and airtime purchases have no mechanism that converts that everyday activity into health savings or insurance cover.
  • Fragmented, untraceable contributions. Where informal or scheme-based health contributions exist, members typically cannot see, per contribution, where their money went — which channel it came through, which ledger it landed in, or which insurer it was allocated to.
  • Manual reconciliation across partners. Telecom operators, banks, and insurers each keep their own records; matching a member's contribution across all three has historically been a manual, error-prone process for the operator running the scheme.

1.1.3Purpose of the system

Tujitunze exists to:

  • Turn routine telecom and bank activity into an automatic, rule-computed contribution toward a member's own health wallet.
  • Make every contribution traceable end-to-end — from the originating webhook, through the contribution ledger, into the wallet, and (where the member holds an active policy) into a specific insurer's allocation.
  • Give each partner in the scheme — telecom operator, bank, insurer, and the platform operator itself — its own tenant-scoped view of exactly its own data, with nothing bled across partners.
  • Keep a full audit trail of the sensitive actions taken against member identity, financial, and health data.

1.1.5Intended use

Tujitunze is intended for continuous, browser-based use: a Member interacts with it to build and monitor a personal health fund; Bank, Telecom, and Insurance staff use it as their partner-facing operations console for that scheme; Admin and Super-admin use it to run and govern the platform. Every role signs in once and is routed to a role-scoped dashboard; a staff account with no tenant assigned is refused access to its own dashboard (403) rather than shown someone else's data or an empty screen.

1.1.6Scope of the system

In scope — real today

  • Member registration, authentication, profile, phone/bank-account linking, and health wallet with a real transaction ledger.
  • Authenticated, signed webhook intake from Telecom and Bank partners that computes a contribution via a configurable rule engine and credits the wallet — proven live, not simulated.
  • Automatic insurance allocation with a fully traceable contribution → wallet transaction → allocation → provider chain.
  • Six of seven role-scoped operational dashboards (Member, Admin, Bank, Telecom, Insurance, Super-admin), each backend-guarded and tenant-isolated.
  • Cross-channel reconciliation, financial reporting, staff provisioning, and a roles/permissions catalog administered by Super-admin.
  • Password reset over email or Tanzanian phone number, rate-limited, OTP-based.

In scope, but not yet live — explicitly deferred

  • Deferred A Vodacom M-Pesa mobile-money adapter (session handling, C2B/B2C/B2B, idempotent payment-transaction recording) exists up to the point of the real provider call, which is blocked on Vodacom's own endpoint documentation rather than left unbuilt.
  • Deferred A usage-quantity-based 6% contribution model (voice minutes / SMS / data) — schema only, zero rows, not wired into any application code.
  • Partial Frontend screens for the Insurance role's claims, settlements, allocation, and reporting endpoints, and for Admin's contribution-summary reporting — the backend is real; no UI consumes it yet.

Out of scope

  • A Hospital staff portal. Not built No backend module or frontend route group exists for hospital staff. The hospitals directory, healthcare_claims, and healthcare_verifications tables remain as reference data, browsed read-only by Members; clinical workflows (check-in, claim filing, appointments) have no owner in the current build.
  • A real external payment rail beyond Tujitunze's own webhook edge — nothing today moves real money at a telecom operator or bank; contribution figures are internal, authenticated bookkeeping until a partner's live systems are pointed at the existing webhook endpoints.
  • Production-grade security hardening (security headers, httpOnly session cookies, distributed rate-limit storage) — see §1.3.2.
  • Real email/SMS delivery — the code paths exist and fail closed, but no production mail or SMS credentials are configured in this environment.

1.2Overall description

1.2.1Software development methodology

Tujitunze is built iteratively: the migration history (23 sequential, additive files in database/migrations/) shows each unit of work landing as an audited, self-contained increment — a migration's own header typically records the audit finding it addresses, what it deliberately does not yet touch, and why. Rather than a single big-bang release, features arrive in phases (for example the payment-transaction layer of migration 0018 was corrected in place by 0019–0023 as the underlying business rule for usage-based contributions was clarified), with each phase re-verified against the running system before the next begins.

Every change is additionally required to pass through a documented six-stage Secure Software Development Life Cycle before it is considered done: Requirements & Planning (state the security requirement alongside the functional one, classify the data touched), Design (threat-model, least-privilege check), Implementation (DTO validation, parameterised queries, guarded endpoints), Verification (a security/code review pass, a boundary-proving test — not just a happy path), Deployment (CORS allowlist, HTTPS, security headers), and Maintenance (audit-log coverage, a living list of known gaps). That known-gaps list is itself treated as a project artefact, not a one-off note — several items closed since baseline are recorded as closed, and what remains open is listed plainly in §1.3.2 rather than omitted.

1.2.2Assumptions and dependencies

Assumptions

  • A member has access to a smartphone or basic phone, an active mobile money/airtime relationship with a partner telecom operator, and/or an account at a partner bank.
  • A member holds or can obtain a NIDA number for identity verification at registration.
  • Staff accounts for Bank, Telecom, Insurance, Admin, and Super-admin roles are provisioned by a Super-admin, not self-registered.
  • Partner telecom operators and banks are willing and able to call Tujitunze's authenticated webhook endpoints from their own systems once integrated.
  • Users interact over a standard modern web browser; no native mobile app exists in the current build.

Dependencies

CategoryDepends on
RuntimeNode.js server for NestJS (backend) and Next.js (frontend); PostgreSQL for persistence
Identity dataNIDA number format/uniqueness at registration
Contribution channelsTelecom operator and bank webhook delivery, authenticated by a per-tenant API key and HMAC signature
Mobile moneyVodacom's M-Pesa Open API — session/C2B/B2C/B2B endpoint documentation, currently the blocking dependency for live mobile-money contributions

Constraints

  • No live mobile-money or bank settlement exists yet; every contribution figure today is internal bookkeeping authenticated at Tujitunze's own edge, not a verified external funds movement.
  • Development environments run with TypeORM synchronize: true and no production security headers — acceptable for local development, explicitly disqualifying for any non-local deployment until closed (§1.3.2).
  • The Hospital role has no functioning staff module — any requirement that assumes hospital-side interaction (claim filing, check-in) is out of scope until that module is built.

Operating environment

  • Server: Linux or Windows host running Node.js, fronting a PostgreSQL database.
  • Client: any modern desktop or mobile browser (Chrome, Firefox, Edge, Safari) over HTTPS in production.
  • Network: internet-connected for both member/staff use and partner webhook delivery.

1.3System features and requirements

1.3.1Functional requirements

Requirements are grouped by role. Each line carries a status chip reflecting what exists in the codebase today, not an aspiration.

a) Member functional requirements

  • RealThe system shall let a citizen register with NIDA number, phone number, and password, and authenticate via JWT.
  • RealThe system shall let a member view and update their profile, and link/unlink phone numbers and bank accounts.
  • RealThe system shall show a member their health wallet balance, top up the wallet directly, and list every wallet transaction with its contribution channel (airtime, bank transfer).
  • RealThe system shall show a member their own insurance plan and claim history, and a membership summary combining identity, wallet, and cover.
  • RealThe system shall notify a member of a wallet top-up, a new linked phone/bank account, a password change, and other sensitive account events.
  • RealThe system shall let a member reset a forgotten password via email token or phone OTP.
  • PartialThe system shall provide a mobile-money account onboarding form; the underlying live mobile-money debit is not yet connected (§1.1.6).
  • Not builtWallet transfer, wallet withdrawal, telecom airtime/bundle purchase-through-wallet, a member-facing QR code, and a member reports screen are placeholders with no backend today.

b) Admin functional requirements

  • RealThe system shall let Admin manage members and hospital-directory reference records, and view/adjust member status.
  • RealThe system shall give Admin a contributions summary and filterable list across channels and statuses, and cross-channel reconciliation checks/runs.
  • RealThe system shall give Admin financial reports with filters and a transaction drill-down.
  • RealThe system shall let Admin read the platform audit log.
  • PartialContribution filtering is channel- and status-based only today; filtering by member, date range, or specific operator/bank is not yet implemented.

c) Bank functional requirements

  • RealThe system shall let Bank staff manage their own bank's profile, contact details, and API/webhook credentials, scoped to their bank_id tenant link.
  • RealThe system shall accept an authenticated, signed webhook from the bank recording a contribution, and let staff manually record, reverse, or fail a transaction.
  • RealThe system shall let Bank manage Tujitunze's own fund accounts and fund transfers held at that bank, and create/complete settlements to Telecom or Hospital partners.
  • RealThe system shall give Bank a three-way reconciliation (Matched / Discrepancy / Unmatched), reports, and activity/API access logs — every page here has a matching frontend screen.

d) Telecom functional requirements

  • RealThe system shall mirror Bank's operator-profile, credentials, contribution recording/reversal, reconciliation, reports, and audit-log capabilities for a Telecom operator.
  • RealThe system shall let Telecom staff view their contribution rules (rate, minimum amount, effective date) read-only.
  • PartialThe system shall expose a Vodacom M-Pesa transaction status query and reversal endpoint; the underlying live provider call is blocked on Vodacom's endpoint documentation (§1.1.6).

e) Insurance functional requirements

  • RealThe system shall let Insurance staff view claims routed to their provider and update claim status.
  • RealThe system shall let Insurance staff view per-contribution allocation records with a full traceability chain back to the originating contribution, plus settlement and reporting endpoints.
  • Not builtNone of the above beyond the summary dashboard has a frontend screen yet — every Insurance capability past the landing dashboard is API-only today.

f) Super-admin functional requirements

  • RealThe system shall let Super-admin provision a staff account for any non-Member role, validating NIDA/email uniqueness and the correct tenant-link requirement for that role.
  • RealThe system shall let Super-admin list every staff account and the available tenants for the provisioning form.
  • RealThe system shall let Super-admin create, rename, delete, and assign permissions to roles, while rejecting a rename/delete of the seven core seeded role names.
  • Not builtThere is no endpoint to edit, deactivate, or reassign a staff account after creation.

g) Hospital — current status

Honest gap, not a partial feature

Hospital is seeded as a role and users.hospital_id still exists as a tenant-link column, but no backend module, controller, or frontend route group implements it. A hospital cannot log in and reach a working dashboard today. The hospitals table, healthcare_claims, and healthcare_verifications persist only as reference data, read (never written) by Member-facing endpoints for hospital-directory browsing and verification history.

Core system processing requirements

  • RealThe system shall authenticate inbound partner webhooks by a per-tenant API key plus an HMAC signature, independent of member JWT auth, via dedicated webhook-intake controllers.
  • RealThe system shall compute each contribution amount from a configurable rule (percentage rate, minimum amount, effective date) rather than a hardcoded constant.
  • RealThe system shall guarantee idempotency on a redelivered webhook — the same external transaction reference shall never produce a second ledger row or a second wallet credit.
  • RealThe system shall credit the wallet and, when the member holds an active policy, create an insurance allocation in the same transaction as the contribution — never as two separate, possibly-inconsistent writes.
  • RealThe system shall record a sensitive write (identity change, financial write, status change, staff/role management action) to the audit log inside the same database transaction as the write itself.

System interaction requirements

  • RealThe system shall serve every role through a single web platform, routing each role to its own path-prefixed dashboard (for example /bank/dashboard, /telecom/dashboard) to avoid Next.js route-group collisions.
  • RealThe system shall enforce every role boundary on the backend (JwtAuthGuard + RolesGuard); the frontend's route-group gate is UX/defense-in-depth only, never the actual authorization boundary.
  • RealThe system shall scope a tenant role's data (Bank/Telecom/Insurance) to its own linked institution and refuse (403) rather than return empty or global data when that link is unset.

1.3.2Non-functional requirements

Performance

  • Dashboard and list endpoints shall respond within normal interactive latency (low hundreds of milliseconds) under expected single-instance load; no dedicated load-testing has been run against this build.
  • Webhook intake shall process a single contribution synchronously within one request/response cycle, including idempotency check, rule computation, ledger write, and allocation.

Usability

  • Each role shall share one consistent dashboard shell (sidebar + layout) so navigation is uniform across every page within that role's route group.
  • A role's navigation shall only list pages that actually exist, to avoid dead links into unbuilt route-group stubs.

Security

Implemented today: JWT + role-based guards on every role-scoped route; tenant scoping by nullable foreign key; DTO validation via a global ValidationPipe; parameterised/query-builder database access throughout; rate limiting on login, registration, phone-number, and super-admin write endpoints; an explicit CORS allowlist; password reset tokens/OTPs stored only as salted hashes with attempt limits and expiry; audit logging on the sensitive write paths listed in §1.3.1.

Still open — treated as required work before any non-local deployment, not silently dropped:

  • OpenNo helmet/security-header middleware is configured.
  • OpenThe JWT is stored in browser localStorage, not an httpOnly cookie — exposed to XSS until session infrastructure is built.
  • Opendatabase.config.ts falls back to a default DB password if DB_PASSWORD is unset, instead of failing closed.
  • OpenTypeORM synchronize: true remains set — acceptable only for local development.
  • OpenRate-limit state is stored in-process and will not be shared once the backend runs behind a load balancer with multiple instances.
  • OpenThe audit log has no pagination or filtering beyond the latest 200 rows.
  • OpenTelecom/Bank webhook_secret is stored retrievable rather than hashed, because Tujitunze needs the raw value to sign outgoing deliveries — a real plaintext-at-rest gap, currently unused by any live code path.

Reliability

  • A failed or ambiguous provider response (network error, timeout, unknown status) shall never be recorded as a successful payment; only a confirmed provider response may mark a transaction SUCCESSFUL — enforced at the database level, not only in application code.
  • Email and SMS delivery shall fail closed (503) when unconfigured rather than silently pretending to have sent something.

Scalability

  • The contribution rule engine, contribution channels, and provider adapters are designed as configuration/data rather than hardcoded constants, so a new operator, bank, or rule can be added without a code change to the core ledger path.
  • Horizontal scaling of the backend is currently constrained by the in-process rate-limiter and session-key cache (§ above) until a shared store is introduced.

Maintainability

  • Schema changes are additive, versioned SQL migrations under database/migrations/, each documenting the audit finding it addresses and what it deliberately leaves untouched.
  • Backend test coverage includes 16 end-to-end spec files and 14 unit spec files exercising authorization boundaries, webhook idempotency, reconciliation, and rate limiting — not just happy paths.

Compatibility

  • The frontend targets evergreen desktop and mobile browsers via Next.js's standard support matrix; no legacy-browser support is targeted.

1.3.3System features

At its centre, Tujitunze gives every member a unified health wallet: one balance, backed by an immutable transaction ledger, regardless of which channel funded it. Feeding that wallet is a multi-channel contribution engine — authenticated webhooks from telecom and bank partners, each run through a configurable rate/minimum rule before a single shared crediting path touches the ledger, so airtime-based and bank-transfer-based contributions can never diverge in how they're recorded. A mobile-money channel via Vodacom M-Pesa is built up to the same idempotent, database-enforced-honesty standard, pending the provider's own endpoint documentation.

Where a member holds an active policy, a contribution automatically produces an insurance allocation, and that allocation is traceable in one query back to the exact contribution and wallet entry that produced it — a design goal the platform can answer concretely today ("where did this member's TZS 20 go?"), not just assert. Sitting over all of this is cross-channel reconciliation: Bank and Telecom can each upload or generate a batch of their own records and have it matched against Tujitunze's ledger, surfacing matches, discrepancies, and unmatched rows.

Six role-scoped operational dashboards give each class of user — Member, Admin, Bank, Telecom, Insurance, Super-admin — only the views and actions that belong to it, backed by the same guard pattern everywhere. A platform-wide audit trail and a notifications system keep members and operators aware of sensitive events as they happen. Finally, Super-admin governance closes the loop: staff accounts and the roles/permissions catalog itself are managed through the same audited, guarded pattern as every other sensitive write, rather than hand-written SQL.

1.3.4Data requirements and data sources

Data requirements

Data classification

Tujitunze handles four categories of sensitive data, each requiring an authorization check and an audit trail: PII (name, NIDA number, address, date of birth), financial (wallet, bank, telecom, and mobile-money transactions), health (insurance policies, claims, verifications), and general administrative data (roles, permissions, tenant links).

Beyond identity and financial data, the system requires: contribution rule configuration (rate, minimum, effective date per rule type); reference data for partner institutions (telecom operators, banks, insurance providers and their plans); and operational data generated by the platform itself — audit log entries, notifications, and reconciliation run records.

Data sources

  • Member self-registration — identity, contact, and initial phone/bank-account linkage, entered directly by the member.
  • Super-admin provisioning — every non-Member staff account and its tenant link.
  • Admin-managed reference data — the hospital directory and member-record corrections.
  • Authenticated partner webhooks — real, live contribution notifications from Telecom and Bank systems, the primary source of ongoing financial transaction data.
  • Vodacom M-Pesa gateway — the mobile-money channel's intended data source once the adapter's remaining wire call is unblocked.
  • Seed/reference data — insurance providers and starter plans (NHIF, Diamond Trust Insurance, Jubilee Insurance) and contribution-rate rules, loaded via versioned migrations so they are reproducible across environments.

System Design

4.1System architecture

Tujitunze follows a layered architecture: a Next.js presentation tier, a NestJS application tier enforcing every real authorization decision, a PostgreSQL data tier reached only through TypeORM, and an external-integration edge that fails closed whenever a provider isn't configured.

4.2.2Database design (overview)

Why this section stops at an overview

The live schema has grown past the point where a column-by-column data dictionary belongs in a requirements document: 23 sequential migrations on top of the base schema, spanning identity, wallet, telecom, bank, insurance, payments, and audit domains. Per the scope agreed for this document, this section describes the design at the level of table groups and the relationships between them (mirroring §2.3's ERD); database/schema/tujitunze.sql and database/migrations/ remain the single source of truth for exact columns, types, and constraints.

The most consequential design decision in the schema is the four-layer contribution chain, added incrementally rather than designed monolithically up front:

  1. telecom_contributions / bank_transactions — the original per-channel contribution ledger, workflow-staged (Pending → Received → Validated → Allocated → Failed → Reversed).
  2. wallet_transactions — the unifying ledger every channel credits through one shared method; the wallet's displayed balance is always a derived total, never itself the source of truth.
  3. insurance_allocations — created in the same transaction as a contribution credit whenever the member holds an active policy, giving a provably traceable contribution → wallet entry → allocation → provider chain.
  4. payment_transactions — a newer layer sitting above the other three, recording a provider's own payment-lifecycle status (INITIATED/PENDING/SUCCESSFUL/FAILED/REVERSED/REFUNDED/DISPUTED/PENDING_REVIEW) distinctly from the ledger's own workflow vocabulary — see Figure 5.

A related, deliberately unwired addition is telecom_usage_events: a table for a usage-quantity-based contribution model (6% of voice minutes / SMS / data consumed, converted to TZS only at a provider-authorised rate — never an invented per-unit price). It holds zero rows and is not read by any controller today; it exists as a reviewed, corrected schema ahead of the application code that will use it.

All schema changes are additive SQL migrations, never a destructive rewrite of a table already carrying data — several migrations in the history explicitly verify "zero rows, safe to correct in place" before altering a table, and none drops or recreates a table that held live data.
